# Pipeline 4.2.0 Multi-Agent Planner Architecture

**GPT-6-Astra (Codex) Execution Results**

Codex has analyzed the goal of triggering robust, N>1 concurrent multi-agent workflows (like SRS/WBS generation) utilizing the CoChem 4.2.0 SQLite WAL `job_board.db` state machine. It has proposed an architecture to completely replace the manual 5-6 round "babysitting" loop with a deterministic SQLite DAG structure.

### Core Architectural Design

#### 1. Workflow State Machine Model
A complex multi-agent planning workflow (e.g. creating an SRS document) is decomposed into a strict Directed Acyclic Graph (DAG) managed inside `job_board.db`.

1. **`MACRO_PLANNING_REQUEST`**: The root job. Triggered via the orchestrator.
2. **`MANIFEST_GENERATOR`**: An agent creates the WBS chunk breakdown (e.g. 6 chapters), which splits into 6 distinct SQLite tasks.
3. **`CHAPTER_DRAFT` (N instances)**: Multiple agents run concurrently, strictly constrained by `hardware_guard.py`. Each agent owns precisely ONE chapter. They submit immutable artifacts to `job_board.db` payload outputs.
4. **`SYNTHESIS`**: A barrier task that is ONLY eligible to execute when all `CHAPTER_DRAFT` tasks for the parent workflow are marked `COMPLETED`. Gemini 3.1 Pro executes this, pulls all outputs, and generates the final master document.

#### 2. Concurrency and Lease Fencing
The architecture explicitly addresses the user's requirement for hardware guardrails.
- **SQLite WAL**: The job board utilizes WAL mode, allowing the `watchdog` to monitor progress without locking readers. 
- **Fencing Tokens**: Every agent execution receives a unique `attempt_id` and a lease from `hardware_guard.py`. If a chapter agent hangs or crashes, the lease expires. A subsequent retry gets a new fencing token. When the original zombie agent wakes up and tries to submit a `COMPLETED` state, the commit is rejected due to a mismatched fencing token.

#### 3. Eradicating Counterfeit Compliance (Anti-Spoofing)
- **Isolation**: Each `CHAPTER_DRAFT` agent is explicitly forbidden from reading sibling chapters during execution to enforce true parallelism and prevent LLM "laziness" where one agent summarizes another's work.
- **Payload Schema**: Agents do not submit free-form text. The `CHAPTER_DRAFT` completion schema requires `requirements_traced`, `wbs_tasks_defined`, and `artifact_uri`.
- **Identity Proofing**: Sub-agents cannot fake the `SYNTHESIS` completion. Synthesis requires the verified output hashes of all N chapters.

#### 4. WBS Implementation Strategy

| Phase | Package | Deliverable |
|---|---|---|
| **Phase 2.1** | State Mapping | Add `parent_job_id` and `fencing_token` columns to `job_board.db` |
| **Phase 2.2** | Scatter Controller | Modify the `worker_daemon.py` to identify `MANIFEST` completion and atomically `INSERT` the `CHAPTER_DRAFT` sibling jobs. |
| **Phase 2.3** | Gather Barrier | Modify `worker_daemon.py` to poll for `parent_job_id` sibling completion status before transitioning the `SYNTHESIS` task from `BLOCKED` to `PENDING`. |
| **Phase 3** | Integration | Update the Claude and Codex MCPs to properly accept the structured payloads generated by the Scatter-Gather nodes. |

### Required Acceptance Criteria
1. One ordinary request creates the workflow without repeated delegation instructions from the user.
2. Six chapters execute with a four-agent limit and at least two overlapping accepted chapter executions (verifying `hardware_guard.py`).
3. An agent attempting to submit a sibling chapter is rejected by the database constraint.
4. Simultaneous final chapter completions release exactly one logical `SYNTHESIS` task.
5. A daemon crash at a launch/commit boundary recovers without accepting duplicate outputs.
